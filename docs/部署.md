# 邻聊 2.5.1 部署说明

本文说明两件事：在本机或内网一台主机上把服务跑起来，以及在需要时如何用自有域名从外网接入。示例使用占位符，例如 `chat.example.com`、`<主机地址>`、`<内网网段>`。不要把填写后的域名、内网地址、主机路径或密码写回仓库。

本文按 2.5.1 源码中已核对的行为写成。反向代理、防火墙和无公网 IP 隧道只作为步骤说明；本次发布验证没有执行它们，不能把这些步骤当成已经通过。

## 1. 本地部署

### 1.1 准备

- 安装 **Node.js 20 或更高版本**以及 npm。`package.json` 的 `engines` 为 `>=20`。锁定依赖 `@httptoolkit/httpolyglot@3.1.0` 声明了 `node >= 20`。`npm run dev` 使用 `node --watch`。
- 取得 2.5.1 源码，目录中需要有 `package.json` 与 `package-lock.json`，以便使用 `npm ci`。
- 一台能被目标用户访问的主机。只给自己用时可以是本机；局域网使用时，这台主机需要和设备在同一可达网络里。

### 1.2 安装依赖并启动

在项目根目录执行：

```bash
npm ci
PORT=9900 npm start
```

`npm start` 实际执行 `node server.js`。**请显式设置 `PORT=9900`。** 未设置时，程序入口为：

```js
const PORT = Number(process.env.PORT || 3080);
```

也就是说会回退到 `3080`。

开发时可以使用：

```bash
PORT=9900 npm run dev
```

这会以 `node --watch server.js` 启动，同样需要显式指定端口。

程序通过 `process.env` 读取配置，**不会自动加载 `.env` 文件**。仓库中的 `.env.example` 只是占位示例。若要使用环境文件，请在启动前自己导出变量，例如：

```bash
set -a
# 仅在本机保存的环境文件，不要提交到 Git
. ./lan-chat.env
set +a
PORT=9900 npm start
```

启动成功后，日志会提示统一端口已开始监听，并打印本机非回环地址。这些地址属于运行这台机器的人，不要把启动日志贴到公开场合。进程收到 `SIGINT` 或 `SIGTERM` 时会关闭 WebSocket 和服务后退出。前台运行时按 `Ctrl+C` 即可。

### 1.3 访问

本机浏览器：

| 入口 | 地址 |
| --- | --- |
| 聊天页面 | http://127.0.0.1:9900/ |
| 管理后台 | http://127.0.0.1:9900/admin |
| 网页录音说明 | http://127.0.0.1:9900/secure-setup.html |

从局域网其他设备访问时，将 `127.0.0.1` 换成这台主机的地址，例如 `http://<主机地址>:9900/`。若已让程序自己提供 TLS，再把 `http` 改成 `https`。

服务在 `server.listen(PORT, '::')` 上监听，同时接受 IPv4 与 IPv6，**并不会自动只绑定 127.0.0.1**。同一局域网的设备可以直接连到该端口。如果这台主机还处在可被更广网络访问的位置，需要靠防火墙或反向代理限制谁能直接访问应用端口。源码中没有单独的“仅监听回环地址”环境变量。

聊天页会按当前页面的协议连接 WebSocket：`ws://<主机>/` 或 `wss://<主机>/`，查询参数中带有设备标识。本机或反代只要放行同一主机、同一端口上对 `/` 的 Upgrade 即可，没有另外的 WebSocket 专用路径。

### 1.4 数据持久化与管理员初始设置

默认数据目录是程序运行目录下的 `data/`。也可以用环境变量 `DATA_DIR` 指向其他位置。其中主要包括：

- 明文保存的消息和撤回状态、群组、设备资料、账号资料
- 账号密码和管理员密码的哈希（管理员密码使用 scrypt）
- 账号多端登录会话和会话签名密钥
- 上传的图片、语音和普通文件（位于数据目录下的 `uploads/`）
- 首次自动生成时写入的管理员密码文件 `admin-password.txt`（权限为仅服务用户可读）
- 设备门禁开启后的 `known-devices.json`，其中只保存设备凭证的 SHA-256 摘要

聊天内容以 JSON 明文存储，**不是端到端加密**。写入 JSON 时会先写临时文件再替换。磁盘空间仍是实际上限，请自行监控容量并备份整个数据目录。

程序本身只静态提供 `public/`，以及按文件名读取 `uploads/`（`index: false`，不列目录）。它不会把 `data/` 下的 JSON 或密码文件映射成网页路径。不要把数据目录配成另一个 Web 服务器的网站根目录，也不要把该目录放进仓库、安装包或可供下载的路径。

管理员密码：

1. 若启动前设置了 `ADMIN_PASSWORD`，则以该值为准。
2. 否则，首次启动会生成随机密码，明文只写在 `admin-password.txt` 中，校验用的哈希另行保存。
3. 在运行服务的这台机器上读取该文件，打开 `/admin` 登录。
4. 不要在文档、截图、日志或聊天里传播该文件内容。

### 1.5 基本验证与停止

```bash
curl http://127.0.0.1:9900/api/health
npm test
```

正常的健康检查响应为 JSON，包含 `"ok": true` 以及 `"version": "2.5.1"`。

`npm test` 执行 `node --test`，覆盖健康检查、匿名与账号身份、文件上传回读、群组成员隔离、隐私群、Agent 读取范围、MCP 调用、双协议和设备门禁。设备门禁集成测试会真实等待约 60 秒。

再在浏览器打开聊天页，确认可以选择身份并进入公共大厅。如需管理功能，用上面的密码登录 `/admin`。

停止前台进程：按 `Ctrl+C`，或向该进程发送 `SIGTERM`。

### 1.6 可选的 systemd 用户服务

`install.sh` 供带有 systemd **用户实例**的 Linux 使用。它会：

1. 检查 `PATH` 上的 Node.js 主版本不小于 20。
2. 把程序复制到 `~/services/lan-chat`，包括 `server.js`、`device-access.js`、`public/`、`test/` 和 `deploy/`。
3. 在安装目录执行 `npm ci --omit=dev` 和 `npm test`。
4. 将 `deploy/lan-chat.service` 中的 Node 路径改写为当前找到的 `node`，再安装到 `~/.config/systemd/user/lan-chat.service`。
5. 若 `~/.config/lan-chat/lan-chat.env` 不存在，则从 `.env.example` 复制一份。该文件由 systemd 的 `EnvironmentFile` 注入；邻聊进程不会自己发现它。
6. 执行 `systemctl --user enable --now lan-chat.service`，并请求 `http://127.0.0.1:9900/api/health`。

服务单元把 `PORT=9900` 写在单元文件里，工作目录是 `%h/services/lan-chat`，只允许写入该目录下的 `data/`。

没有 systemd 用户实例时，脚本会在完成复制、`npm ci` 和 `npm test` 后以非零状态退出，并提示改用 `PORT=9900 npm start`。非零状态在这里表示开机服务没有启用；测试若失败，脚本会更早退出，并且不会打印“自动测试已完成”。本次发布验证环境没有用户级 systemd，因此没有执行 `enable --now`，也不把这一步记为通过。详见第 5 节。

若你的系统需要用户服务在注销后仍运行，那是 systemd 的 linger 设置，需你自己在目标机器上决定。本文不代为修改登录策略。

### 1.7 已核对的环境变量

| 变量 | 说明 |
| --- | --- |
| `PORT` | HTTP/HTTPS 共用端口。启动示例为 `9900`；未设置时回退到 `3080` |
| `DATA_DIR` | 可选，数据目录 |
| `ADMIN_PASSWORD` | 可选，覆盖首次生成的管理员密码 |
| `MAX_UPLOAD_BYTES` | 可选上传上限（字节）。不设或设为 `0` 表示不限制大小 |
| `TLS_CERT_PATH` / `TLS_KEY_PATH` | 仅当由邻聊进程自己提供 HTTPS 时需要 |
| `CA_CERT_PATH` | 可选，供局域网设备下载的 CA 证书，对应 `/lan-chat-ca.crt` |
| `REQUIRE_HTTPS=1` | 仅在进程已启用 TLS 时有意义。默认仍允许 HTTP 聊天。TLS 已配置时，管理后台会要求 HTTPS，即使未设置此项 |
| `TRUST_PROXY=1` | 仅在受控反向代理之后开启。影响资料与登录限速所看到的客户端地址 |
| `PUBLIC_MCP_URL` | MCP 对外地址。请设成你自己的 `https://<你的域名>/mcp`。未设置时使用占位 `https://chat.example.com/mcp` |
| `DEVICE_ADMISSION_ENABLED=1` | 开启设备接入门禁。默认关闭 |
| `DEVICE_LAN_CIDRS` | 逗号分隔的内网 CIDR。未设置时没有任何地址被当作内网 |
| `DEVICE_LAN_EXCLUDED_IPS` | 逗号分隔的地址。即使落在上面的 CIDR 内，也不享受内网豁免。请填入网关、本机和其它基础设施地址 |
| `DEVICE_ALLOWED_HOSTS` | 逗号分隔的 Host 名。除了与套接字本地地址相同的 Host 之外，还必须列出用户实际打开的域名，否则门禁会拒绝该 Host |

`TRUST_PROXY` 与设备门禁采信转发头不是同一条规则。门禁只在 TCP 对端已经是 `127.0.0.1` 或 `::1` 时，接受**一个**合法的 `X-Forwarded-For`。带逗号的多段转发头不会被当成内网地址。公网客户端直接连到邻聊时，伪造该头无效。`TRUST_PROXY=1` 另外让资料和登录限速使用同样的“仅回环、仅单个地址”规则。

可选 MCP 代理还有 `MCP_PROXY_HOST`、`MCP_PROXY_PORT`（默认 443）、`MCP_PROXY_LISTEN`（默认 `::`）、`MCP_UPSTREAM_HOST`（默认 `127.0.0.1`）、`MCP_UPSTREAM_PORT`（默认 `9900`）、`TLS_CERT_PATH` / `TLS_KEY_PATH` 或 `MCP_CERT_REGISTRY`。见第 2.4 节。

## 2. 外网接入：先分清两层

把服务暴露到外网时，请把**应用层**和**网络层**分开配置。邻聊提供网页、WebSocket、上传下载、管理后台和 MCP。它不负责申请域名、签发公网证书，也不会在路由器上打开端口。

推荐做法：使用你自己的域名，由反向代理终止 HTTPS，再把流量转到本机的邻聊进程。不要把应用端口（示例中的 `9900`）直接做端口映射。

### 2.1 应用层要做的

1. 仍用 `PORT=9900 npm start` 在目标主机启动，或由你自己的进程管理器注入同样的变量。
2. 用主机防火墙限制该端口，不要让它被公网直接访问。让反向代理从本机回环或仅内网可达的地址转发到 `9900`。
3. 若 TLS 由反向代理负责，不要再给邻聊进程配置 `TLS_CERT_PATH` / `TLS_KEY_PATH`，让它在代理后面走 HTTP。
4. 在反代之后设置 `TRUST_PROXY=1`。反代应只提交一个客户端地址，并运行在邻聊看来是回环的地址上。
5. 显式设置 `PUBLIC_MCP_URL=https://chat.example.com/mcp`，并把主机名换成你的域名。
6. 按需要开启 `DEVICE_ADMISSION_ENABLED=1`。同时设置 `DEVICE_LAN_CIDRS`、`DEVICE_LAN_EXCLUDED_IPS` 和 `DEVICE_ALLOWED_HOSTS`。门禁不能代替 HTTPS。
7. 不要把管理后台和数据目录当作对公众开放的入口。

### 2.2 网络层：主机已有公网 IP

条件：这台主机拥有可被公网路由的 IPv4 或 IPv6 地址，并且你拥有一个域名。

1. 将域名解析到该主机。有公网 IPv4 时配置 **A 记录**；只有公网 IPv6 时配置 **AAAA 记录**。
2. 在主机上运行反向代理（例如 Caddy 或 nginx），监听 443，用你自己的证书提供 HTTPS。
3. 把站点流量，包括 WebSocket 升级，转到 `127.0.0.1:9900`。聊天页的 WebSocket 使用当前主机的 `/`。
4. 只把 443，以及你用于申请证书的 80（如需要），对公网开放。不要开放或映射 `9900`。
5. 反向代理往往默认限制请求体大小。邻聊默认不限制单文件大小。若要传大文件，请按自己的需求调高反代上限。

下面两段是配置形状示例。**本次发布验证没有运行 Caddy 或 nginx，也没有申请证书。**

Caddy 示例：

```caddy
chat.example.com {
	reverse_proxy 127.0.0.1:9900
}
```

nginx 示例：

```nginx
map $http_upgrade $connection_upgrade {
    default upgrade;
    '' close;
}

server {
    listen 443 ssl;
    server_name chat.example.com;
    # ssl_certificate     /path/to/fullchain.pem;
    # ssl_certificate_key /path/to/privkey.pem;
    # client_max_body_size 0;

    location / {
        proxy_pass http://127.0.0.1:9900;
        proxy_http_version 1.1;
        proxy_set_header Upgrade $http_upgrade;
        proxy_set_header Connection $connection_upgrade;
        proxy_set_header Host $host;
        proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
        proxy_set_header X-Forwarded-Proto $scheme;
    }
}
```

配置完成后，用浏览器访问 `https://chat.example.com/`。健康检查可以是：

```bash
curl https://chat.example.com/api/health
```

若 MCP 也走同一域名，对外地址应是 `https://chat.example.com/mcp`，并与 `PUBLIC_MCP_URL` 一致。

若主机启用了防火墙，只放行你信任的来源访问应用端口。下面是形状示例，**本次没有执行**，其中的网段必须换成你自己的：

```bash
sudo ufw allow from <内网网段> to any port 9900 proto tcp
```

因为进程监听所有地址，未加防火墙时，同一二层或可路由网络中的主机都可以直接连接 `9900`。

### 2.3 网络层：没有公网 IP

若主机没有可从公网直接访问的地址，本项目不能凭自身变成一个公网站点。可以选择：

- **仅内网使用。** 设备与服务器在同一可达的私网中，用 `http://<主机地址>:9900/` 访问。此方式是明文 HTTP，只适合可信局域网。网页直接录音在这种地址下通常不可用，见第 3 节。
- **由你自己配置的 HTTPS 隧道或零信任接入。** 把公网域名转到本机 `9900`。这不是邻聊内置功能，仓库里没有开通脚本，也没有针对某一家隧道产品做即插即用适配。本次发布验证没有创建或连接任何隧道。若采用这种方式，应用层仍按 2.1 设置 `TRUST_PROXY` 与 `PUBLIC_MCP_URL`，并确认隧道支持 WebSocket。

不要为了从外面打开页面，而把路由器端口直接转到邻聊的应用端口。

### 2.4 可选的 MCP HTTPS 代理

`deploy/mcp-https-proxy.mjs` 是一个很小的 HTTPS 反向代理，只放行：

- `/mcp`
- `/.well-known/neighbor-chat-mcp`

其它路径返回 404，因此它不会把聊天页、管理后台或数据目录转出去。上游默认是 `127.0.0.1:9900`。

证书必须由你提供，二选一：

- `TLS_CERT_PATH` 与 `TLS_KEY_PATH`
- `MCP_CERT_REGISTRY` 指向一个 JSON 数组，元素包含 `host`、`cert`、`key`，其中 `host` 等于 `MCP_PROXY_HOST`

未配置证书时进程会退出。默认监听 `::` 的 `443`，这需要相应权限，并且同样受防火墙约束。非特权试验请设置 `MCP_PROXY_PORT` 和 `MCP_PROXY_LISTEN`。

证书路径发生变化时，进程每 60 秒尝试热更新一次。同一路径上的文件内容被覆盖时，不会因为内容变化而自动重载，需要重启进程。

自动测试用临时证书检查了路径白名单和上游转发。它没有在 443 上对公网做过部署，也不能代替第 2.2 节的站点反代。聊天页面的 WebSocket 不经过这个代理。

## 3. 安全上下文、身份边界和公网风险

### 3.1 麦克风与安全上下文

页面内长按录音依赖浏览器的安全上下文：通常只有 `https://`，或本机的 `http://localhost` 与 `http://127.0.0.1`。用局域网 IP 或主机名走明文 HTTP 时，浏览器一般会拒绝网页直接打开麦克风。这时界面会改为选择已有的录音文件再发送。需要网页内录音时，请准备浏览器信任的 HTTPS，而不是指望在明文 IP 上调用麦克风。

### 3.2 账号、匿名、门禁与后台

- **匿名：** 资料跟随当前设备。匿名身份不能使用 MCP。门禁关闭时，选择匿名使用会进入聊天，不会先做设备登记。
- **注册账号：** 可在多台设备同时在线，并可创建不会出现在公共列表中的隐私群。账号名与密码长度见首页。
- **设备接入门禁（默认关闭）：** 只有 `DEVICE_ADMISSION_ENABLED=1` 才生效。已登记客户端持有独立的 HttpOnly Cookie。未登记的外网设备在读取页面、调用接口或建立 WebSocket 之前会被拒绝。账号密码本身不能绕过。已登录账号可以开启接入窗口；窗口固定 **60 秒**，请求体里的时长会被忽略。服务重启后，进行中的窗口关闭，已经登记的设备仍然有效。凭证表示“持有该 Cookie 的客户端”，不是不可复制的硬件身份。浏览器也不会把网卡 MAC 交给网页。
- **Host 允许列表：** 门禁会拒绝不在 `DEVICE_ALLOWED_HOSTS` 中、且不等于本次连接本地地址的 Host，用来降低 DNS 重绑定把内网访问登记成外网来源的可能。用域名访问时请把该域名列入允许列表。
- **管理后台：** 入口为 `/admin`。不要在未加密链路上从不可信网络登录，也不要把它裸露到公网。

开启门禁后，公网 MCP 在账号令牌之外还需要已登记的设备 Cookie。建议在窗口内完成首次 `initialize` 并保存 `Set-Cookie`，之后每次请求带上它。这不会扩大该账号原有的群组权限。

### 3.3 公网环境下务必清楚的限制

- 消息与文件在服务器上是明文存储。传输层安全取决于你是否正确配置了 HTTPS。**没有端到端加密。**
- 若跳过反代、把应用端口直接暴露到公网，聊天、会话、文件和管理入口都会出现在同一端口上。
- 任何能连到本机回环地址的进程，都可以提供单个 `X-Forwarded-For`，从而被门禁当作那个地址。只应让你自己的反代这样做。
- 设备门禁和账号登录都不能替代 HTTPS，也不能代替你对管理后台和数据目录的访问控制。
- 源站监听所有地址。只配置应用、不配置防火墙时，可达网络里的主机都能直接连接服务端口。

## 4. 已知安装限制

- 本版本是网页服务，不包含应用商店里的独立 App，也不包含音视频通话。
- 可移植的启动方式是 `PORT=9900 npm start`。`install.sh` 的 systemd 启用步骤依赖用户级 systemd；没有该环境时不要把它理解成已经安装成开机服务。
